## 1. Executive Summary

The marathon test proved the core orchestration loop is functional: 44+ tasks processed across 4 devices, queue fill/review/finalize pipeline works, agent identity and dropbox workflows operate end-to-end. However, the run exposed systemic issues across **four categories** that must be resolved before the next extended autonomous session:

### Category A — Task Quality & Output Integrity

- **130+ near-identical speculative feature request tickets** flooded the outbox — the novelty gate problem
- **Zero post-task quality verification** — tasks marked "completed" with empty or irrelevant output, including pseudo-code passed off as implementation
- **No cross-task artifact threading** — follow-up tasks cannot access parent task output; completed task `result` is saved but never injected as context for subsequent work
- **Preflight analysis (GOAL/CONSTRAINTS/RISKS/APPROACH) is advisory-only** — the system generates it but never checks the output against it
- **Queue-fill review VERDICT is cosmetic** — whether the reviewer says "approve" or "revise" does not programmatically change the flow
- **Self-improvement tasks restart from scratch** instead of iterating on prior artifacts with explicit deltas
- **Context reset loops** — no artifact lineage means each cycle lacks explicit reference to what was already produced

### Category B — Model & Resource Management

- **Model drift** — gpt-oss:20b used for 10 tasks, qwen3-coder for 7 — no model family lock or swap penalty awareness
- **No model profile modes** (`all-llamas` / `custom` / `auto`) — requested in incident log and remediation plan
- **Resources sit idle** while orchestrator processes serially (no per-resource backlogs)
- **Excessive polling** (twice/minute per device for version/tags)
- **Agent identities conflated with device resources** — no separation of identity from hardware
- **Wikipedia misused for internal Local Crew diagnosis** instead of being limited to factual grounding

### Category C — Observability & CLI

- **SSE display data is bare-minimum** — only counts and busy flag; no task results, no preflight output, no resource assignments, no throughput metrics
- **CLI `/status` viewer shows stale data** — fetched once, never refreshed, redraws on every garbage keypress
- **CLI `/hud` flickers** — 250ms full-screen erase/redraw cycle with no dirty-checking
- **CLI `/explore` re-fetches disk I/O on every keystroke** — no caching
- **No alternate screen buffer** — viewer output pollutes terminal scrollback
- **No label-first entity rendering** — raw aliases shown where `Label (alias)` format is expected

### Category D — Architectural Gaps

- **Context management** is broad-and-shallow instead of hot-swapped and targeted; the remediation plan considers context bundles P0-critical, not Day 3
- **No daily session lifecycle** — `DAILY_COMPLETE` signaling, digest generation, and session bounding are all directives-level requirements with no implementation
- **No failure diagnosis or quarantine** — failed tasks get a status flag but no structured recovery workflow
- **No task clarity validation** — directives require "clear object, scope, and expected outcome" but the classifier only checks type/reasoning-depth
- **Stack-aware language guardrails missing** — model can suggest Python scripts for a TypeScript-only repo
- **Resource alias validation absent** — nothing prevents task routing attempts using participant aliases instead of resource roster names

**This plan replaces and supersedes the prior ticket pack (TKT-01 through TKT-13) with a cohesive phased architecture that addresses the consultant's recommendations, marathon evidence, and remediation plan findings while respecting the zero-dependency TypeScript codebase.**

### Key Observations

1. **Outbox ticket flood:** The queue fill loop generated speculative external-change tasks that got properly redirected to outbox feature request tickets — but the same speculative pattern repeated across dozens of queue-fill cycles, producing ~130 near-identical tickets about telemetry endpoints, metrics scripts, HUD widgets, and cleanup scripts.

2. **Model selection chaos:** `gpt-oss:20b` was used for 10 tasks and `qwen3-coder:latest` for 7 — these are high-VRAM models that cause swap pressure on constrained devices. The system lacks model swap penalty awareness and model family locking.

3. **Serial processing:** Tasks executed one-at-a-time through the orchestrator, leaving 3 of 4 devices idle most of the time. No per-resource work queues exist.

4. **Identity confusion:** Resource aliases like `@desktop-m01slkb` appear in output where participant nicknames should. Agent identities and devices are loosely coupled. The developer review confirms "internal diagnostics now distinguish connected resource aliases from contributor chat participants" as a recent fix, but the separation is not enforced at the type level.

5. **Context reset loops:** Self-improvement tasks restart from scratch each cycle instead of iterating on prior artifacts with explicit deltas. Completed task `result` is stored in `systemState.auto.completed[]` but **never read as input** for any follow-up task.

6. **Polling overhead:** Agent monitors hit Ollama `/api/version` and `/api/tags` every 30 seconds — unnecessary load on inference endpoints.

7. **Quality gate bypass:** The three-phase queue fill pipeline (draft → review → finalize) has the right structure, but the reviewer's VERDICT is **never programmatically parsed** — whether the reviewer says "approve" or "revise" has zero effect on the finalize step. Review is cosmetic.

8. **Output verification absent:** Tasks are marked "completed" immediately after the model returns a response. No check validates that the response is substantive, addresses the task, or meets the preflight GOAL. Empty, irrelevant, or pseudo-code responses all get "completed" status.

9. **Preflight wasted:** `runTaskPreflight()` generates a structured GOAL/CONSTRAINTS/RISKS/APPROACH analysis, but it is silently swallowed on failure (`catch { return null; }`) and when it succeeds, it is only appended as context — the output is never compared against the preflight plan.

10. **Wikipedia misuse:** The model used Wikipedia to answer questions about Local Crew's own internal state. Auto prompts were tightened but no programmatic guard prevents recurrence.

11. **SSE observability gap:** `pushDisplayState()` sends only counts, busy flag, and next/last task content. No task results, preflight analysis, queue-fill reasoning, file write outcomes, error details, resource/model assignment, or throughput metrics reach the display.

12. **CLI viewer bugs:** `/status` shows stale data (fetched once, never refreshed). `/hud` flickers at 250ms with full-screen erase. `/explore` re-fetches disk I/O on every keystroke. No viewers use alternate screen buffer — all pollute scrollback.

## 3. Architecture Realignment

### Current Model (v0.17)

```
LocalCrewApp (monolith) → chooseResourceForTask (regex heuristic) → callModel → single serial loop
```

### Target Model (v0.18)

```
Orchestrator Identity (memory/directives/index)
  ├── Context Bundle Manager (hot-swap memory segments by task purpose)
  │     ├── directives (always)
  │     ├── run-state (recent completions, failures, failure-digest)
  │     ├── artifact-lineage (parent task results for iterative work)
  │     ├── resource-policy (model profiles, context budgets)
  │     ├── focus-alignment (focus-todo + roadmap)
  │     └── domain-knowledge (external memory seeds, user-profile)
  ├── Task Quality Controller
  │     ├── Pre-task: preflight analysis (GOAL/CONSTRAINTS/RISKS/APPROACH)
  │     ├── Post-task: output verification (substance check, artifact check, goal alignment)
  │     ├── Queue-fill: VERDICT enforcement (approve/revise/reject parsed and enforced)
  │     ├── Iteration: cross-task artifact threading (parent result → child context)
  │     └── Guards: task clarity validation, stack language guardrails, Wikipedia scope
  ├── Task Scheduler (per-resource backlogs with back-pressure)
  │     ├── Resource A backlog → inference calls
  │     ├── Resource B backlog → inference calls
  │     └── Resource C backlog → inference calls
  ├── Agent Identity Factory (markdown-based, dynamically created)
  │     ├── Agent "data-analyst" → bound to Resource B
  │     ├── Agent "reviewer" → bound to Resource A
  │     └── Agent "utility-worker" → rotates across low-tier resources
  ├── Capability Scorer (hardware-aware, load-aware, context-aware)
  ├── Model Selector (task-purpose-aware, swap-penalty-aware, profile-lockable)
  ├── Daily Session Manager (DAILY_COMPLETE lifecycle, digest generation)
  └── Telemetry & Observability
        ├── SSE event enrichment (task results, resource assignments, throughput)
        ├── CLI alternate-screen viewers with dirty-checking
        └── Fuzzy T/s estimation from response headers
```

### Core Principles (from consultant + marathon evidence + codebase reality)

1. **Quality over quantity.** Fewer, clearer, better-justified tasks with verified outputs beat high-volume speculative work. "Measure twice, cut once."
2. **Every quality gate must be enforced programmatically.** Prompt-only guardrails are necessary but insufficient — the model will ignore them under context pressure. Every gate needs a code-level enforcement path.
3. **Iterate, don't restart.** Follow-up tasks must receive parent task results as explicit context. Cross-task artifact threading is mandatory for multi-step work.
4. **Devices are resources; agents are identities.** Device names are local, untracked, dynamically created at install. Agent identities are portable markdown bundles.
5. **Increase context before increasing model size.** Never auto-upgrade models.
6. **Prefer horizontal scaling** (more resources working in parallel) over vertical (bigger models on one device).
7. **Measure before routing.** Use capability scores, not just regex keyword matching.
8. **Hot-swap context, don't dump everything.** Load only the memory bundles needed for the current task purpose.
9. **Maintain back-pressure.** Keep every resource's backlog populated so nothing idles.
10. **Favor stability over theoretical max.** Conservative context caps. Never exceed tier limits.
11. **Observability must be comprehensive.** Both CLI and display must show task quality signals, resource assignments, and throughput — not just counts.
12. **Stack awareness.** Generated code and suggestions must match the repository's language and toolchain (TypeScript/Node for this repo).

## 5. Phase 1 — Task Quality Enforcement & Iteration Guidance

*The highest-impact gap from the marathon. Without this, every subsequent phase produces volume without quality.*

### Problem Statement

The marathon produced 44 completed tasks with zero quality verification. The existing quality architecture has the right *structure* (preflight analysis, three-phase queue fill with review) but every gate is advisory-only — the system trusts model output unconditionally. This produced:
- Empty/irrelevant completions marked as successful
- Pseudo-code passed off as implementation
- Self-improvement loops that restart from scratch each cycle
- Follow-up tasks with zero context from their parent task
- Queue-fill review VERDICT that is cosmetic (not enforced)

### 1A: Post-Task Output Verification Gate

**Problem:** After `callModel()` returns, the result is immediately accepted. No validation.

**Implementation in `src/app.ts`:**

```typescript
interface TaskVerificationResult {
  passed: boolean;
  reason: string;
  qualitySignals: {
    substantive: boolean;      // Output is non-trivial (>50 chars of non-boilerplate)
    addressesTask: boolean;    // Output references key terms from task content
    artifactsVerified: boolean; // All claimed WRITE blocks produced real files
    goalAligned: boolean;       // If preflight GOAL exists, output addresses it
  };
}

function verifyTaskOutput(
  task: AutoQueueTask,
  output: string,
  preflightGoal: string | null,
  writtenFiles: string[]
): TaskVerificationResult {
  const signals = {
    substantive: isSubstantiveOutput(output),
    addressesTask: outputAddressesTask(output, task.content),
    artifactsVerified: verifyWrittenArtifacts(writtenFiles),
    goalAligned: preflightGoal ? outputAlignedWithGoal(output, preflightGoal) : true,
  };
  const passed = signals.substantive && signals.artifactsVerified;
  return { passed, reason: formatVerificationSummary(signals), qualitySignals: signals };
}
```

**Substantive output check:**
```typescript
function isSubstantiveOutput(output: string): boolean {
  // Strip common boilerplate prefixes
  const stripped = output
    .replace(/^(Sure|Of course|I'll|Let me|Here's|Certainly)[^.]*\.\s*/gi, "")
    .replace(/\n---+\n/g, "")
    .trim();
  return stripped.length >= 50;
}
```

**Task-content alignment check:**
```typescript
function outputAddressesTask(output: string, taskContent: string): boolean {
  // Extract key nouns from task content (skip stop words)
  const taskTerms = extractContentTerms(taskContent);
  // Check that at least 30% of key terms appear in output
  const found = taskTerms.filter((t) => output.toLowerCase().includes(t.toLowerCase()));
  return found.length >= Math.ceil(taskTerms.length * 0.3);
}
```

**On verification failure:**
- Mark task as `"failed"` with `errorMessage` containing the verification summary
- Log structured audit event with quality signals
- Push enriched SSE event with failure reason
- Do NOT auto-queue remediation (avoids infinite retry loops)
- Limit: max 2 consecutive failures on same resource before marking resource as degraded for this session

### 1C: Queue-Fill VERDICT Enforcement

**Problem:** The review phase generates a VERDICT line ("approve" / "revise" / "reject") but it is never parsed or enforced.

**Implementation in `src/app.ts`:**

```typescript
function parseReviewVerdict(reviewFeedback: string): "approve" | "revise" | "reject" {
  const verdictMatch = reviewFeedback.match(/VERDICT:\s*(approve|revise|reject)/i);
  if (!verdictMatch) return "revise"; // Default to revise if unparseable
  return verdictMatch[1].toLowerCase() as "approve" | "revise" | "reject";
}
```

**Enforcement:**
- `"approve"` → proceed to finalize with draft + review as context
- `"revise"` → proceed to finalize with draft + review as context (current behavior, but now logged as "revised submission")
- `"reject"` → skip finalize entirely, log "Queue fill cycle rejected by reviewer", do NOT fall back to generic tasks. Instead, wait for next natural queue fill trigger.

**This prevents the current behavior where a "reject" verdict still produces finalized tasks via the generic fallback path.**

### 1D: Task Clarity Validation

**Problem:** The directives require "Every autonomous task must have a clear object, scope, and expected outcome." The current `isLowInformationAutonomousTask()` only catches bare one-word verbs.

**Enhancement in `src/app.ts`:**

```typescript
function isTaskClearEnough(content: string): { clear: boolean; reason: string } {
  // Must have at least 8 words
  const words = content.trim().split(/\s+/);
  if (words.length < 8) {
    return { clear: false, reason: "Too short — task must describe object, scope, and expected outcome" };
  }
  
  // Must contain a verb + object structure (not just "Review" or "Implement system")
  // Check for presence of specificity markers: file paths, module names, quoted terms, numbers
  const hasSpecificity = /["'`]|\.ts|\.md|\.json|\d+|specific|particular|exactly/i.test(content);
  if (!hasSpecificity && words.length < 15) {
    return { clear: false, reason: "Lacks specificity — no file paths, quoted terms, or concrete references" };
  }
  
  return { clear: true, reason: "OK" };
}
```

**Integration:** Called in `addPendingTask()` and in queue-fill finalize parsing. Tasks that fail clarity are logged and suppressed (not re-queued).

### 1E: Stack-Aware Language Guardrails

**Problem:** The model can suggest Python scripts, bash utilities, or other non-TypeScript deliverables for a TypeScript-only repository.

**Implementation in `src/messages.ts`:**

Add to auto task system prompt:
```
STACK CONSTRAINT: This repository uses TypeScript with Node.js built-in APIs only. 
Zero external dependencies. All code deliverables MUST be TypeScript (.ts files). 
Do NOT suggest Python scripts, bash scripts, or solutions requiring npm packages 
unless the task explicitly requests a standalone script for a specific platform 
(e.g., setup scripts in scripts/).
```

**Implementation in `src/app.ts` — outbox write guard:**
- When processing `WRITE[outbox]` blocks, if the filename ends in `.py`, `.sh`, `.ps1`, or `.rb` and the task did not originate from a user-submitted request referencing scripts, redirect to a feature-request with a note: "Redirected: non-TypeScript deliverable written to feature request for operator review."

### 1F: Preflight-to-Output Alignment Check

**Problem:** `runTaskPreflight()` generates GOAL/CONSTRAINTS/RISKS/APPROACH but the output is never compared against it.

**Implementation in `src/app.ts`:**

1. When preflight succeeds, extract the GOAL section text
2. After task output, pass GOAL + output to `verifyTaskOutput()` (1A above)
3. The `goalAligned` signal checks whether the output contains key terms from the GOAL
4. If preflight fails (returns null), skip goal alignment — don't block the task

**This closes the loop: preflight → execution → verification → status.**

**Files:** `src/app.ts`, `src/types.ts`, `src/messages.ts`, `src/utils.ts`, `test/app.test.ts`

### 2A: Alternate Screen Buffer

**All viewers must enter/exit the terminal alternate screen buffer:**

```typescript
function enterAlternateScreen(stdout: NodeJS.WriteStream): void {
  stdout.write("\u001b[?1049h"); // Enter alternate screen
  stdout.write("\u001b[?25l");   // Hide cursor (optional, reduces flicker)
}

function exitAlternateScreen(stdout: NodeJS.WriteStream): void {
  stdout.write("\u001b[?25h");   // Show cursor
  stdout.write("\u001b[?1049l"); // Exit alternate screen — original content restored
}
```

**Benefits:**
- Viewer output stays off the main scrollback
- When viewer exits, the original terminal content is restored automatically (no blank flash)
- No need for `clearScreen()` on exit

### 2B: Dirty-Checked Rendering

**Replace the clear-then-redraw pattern with cursor-home-then-overwrite:**

```typescript
function renderFrame(stdout: NodeJS.WriteStream, lines: string[], prevLines: string[]): void {
  stdout.write("\u001b[H"); // Cursor home (top-left)
  
  for (let i = 0; i < lines.length; i++) {
    if (lines[i] !== prevLines[i]) {
      stdout.write(`\u001b[${i + 1};1H`);    // Move to line i+1
      stdout.write("\u001b[2K");               // Clear line
      stdout.write(lines[i]);
    }
  }
  
  // Clear any remaining lines from previous frame
  for (let i = lines.length; i < prevLines.length; i++) {
    stdout.write(`\u001b[${i + 1};1H\u001b[2K`);
  }
}
```

**This eliminates the blank flash between clear and redraw — only changed lines are rewritten.**

## 9. Phase 5 — Context Safety & Hot-Swap Architecture

*Enforce context caps by tier. Replace broad context dumping with targeted, purpose-aware memory loading. Context bundles are architecturally critical — without them, every auto task receives the same bloated context regardless of purpose, wasting tokens and degrading output quality.*

|---|---|---|
| O (top/orchestrator) | 32768 | Mac M4 32GB can handle this |
| S (sub-orchestrator) | 16384 | Win 24-core 15.7GB (Zora) |

### 5A: Context Cap Enforcement

```typescript
export function getContextCap(resource: ResourceProfile): number {
  if (resource.maxContextTokens && resource.maxContextTokens > 0) {
    return resource.maxContextTokens;
  }
  // Tier-based defaults
  switch (resource.tier) {
    case "top": return 32768;
    case "mid": return 16384;
    case "low": return 4096;
  }
}

export function computeSafeContextAllocation(
  resource: ResourceProfile,
  telemetry: ResourceTelemetry,
  task: TaskMetadata
): number {
  const desired = task.tokenEstimate * 2; // Room for response
  const cap = getContextCap(resource);
  let ctx = Math.min(desired, cap);
  
  if (telemetry.ramUsagePct > 85) ctx = Math.floor(ctx * 0.5);
  
  return Math.max(ctx, 2048);
}
```

## 10. Phase 6 — Dynamic Model Selection & Profile Modes

### 6A: Model Profile Modes

**Problem:** The incident log and remediation plan both require model profile modes with exactly three options. The operator needs a way to lock model selection to a known-good family.

**New command: `/model profile {mode}`**

| Mode | Behavior |
|---|---|
| `all-llamas` | Only select models matching `llama*` on all resources. Rejects non-llama assignments. |
| `custom` | Use the explicit per-resource purpose assignments in `.localcrew/resources.json`. No auto-selection. |
| `auto` | Dynamic best-fit selection from available models using swap penalty + capability scoring. (Default) |

**Implementation in `src/resources.ts`:**

```typescript
export type ModelProfileMode = "all-llamas" | "custom" | "auto";

let activeModelProfile: ModelProfileMode = "auto";

export function setModelProfile(mode: ModelProfileMode): void {
  activeModelProfile = mode;
}

export function getModelProfile(): ModelProfileMode {
  return activeModelProfile;
}

export function selectModelForTask(
  resource: ResourceProfile,
  task: TaskMetadata,
  currentlyLoaded: string | null
): { model: string; swapRequired: boolean; swapPenaltyMs: number } {
  // Profile lock check
  if (activeModelProfile === "all-llamas") {
    const llamaModel = findModelByFamily(resource, "llama");
    if (!llamaModel) throw new Error(`No llama model available on ${resource.alias}`);
    return { model: llamaModel, swapRequired: currentlyLoaded !== llamaModel, swapPenaltyMs: 0 };
  }
  
  if (activeModelProfile === "custom") {
    const purpose = detectTaskPurpose(task);
    const model = selectModel(resource, purpose); // Uses explicit purpose slots only
    return { model, swapRequired: currentlyLoaded !== model, swapPenaltyMs: 0 };
  }
  
  // "auto" mode — full scoring with swap penalty
  const optimalModel = selectModel(resource, detectTaskPurpose(task));
  const swapRequired = currentlyLoaded !== null && currentlyLoaded !== optimalModel;
  const swapPenaltyMs = swapRequired ? estimateSwapPenalty(optimalModel) : 0;
  
  if (swapRequired && swapPenaltyMs > 5000 && canModelHandleTask(currentlyLoaded!, task)) {
    return { model: currentlyLoaded!, swapRequired: false, swapPenaltyMs: 0 };
  }
  
  return { model: optimalModel, swapRequired, swapPenaltyMs };
}

function findModelByFamily(resource: ResourceProfile, family: string): string | null {
  // Check purpose slots, then available models
  for (const model of [resource.defaultModel, resource.reasoningModel, resource.codingModel, resource.toolsModel]) {
    if (model && model.toLowerCase().startsWith(family)) return model;
  }
  return null;
}
```

```typescript
  // Distribute pending tasks across resource backlogs
  distribute(
    pending: AutoQueueTask[],
    resources: ResourceProfile[],
    telemetry: Map<string, ResourceTelemetry>,
    scorer: (resource: ResourceProfile, task: TaskMetadata) => number  // Phase 4's computeResourceScore()
  ): void;
  
  // Get next task for a specific resource
  dequeue(resourceAlias: string): AutoQueueTask | null;
  
  // Check if any resource has capacity
  hasCapacity(): boolean;
  
  // Get back-pressure status
  getBackPressure(): Map<string, { depth: number; maxDepth: number }>;
  
  // Rebalance when resource comes online/offline
  rebalance(): void;
}
```

**Integration with auto-pulse:**

```typescript
// BEFORE: single serial task processing
async pulse(): Promise<void> {
  const nextTask = this.getNextPendingTask();
  if (nextTask) await this.processTask(nextTask);
}

// AFTER: parallel resource processing
async pulse(): Promise<void> {
  const idleResources = this.scheduler.getIdleResources();
  const taskPromises = idleResources.map(async (resource) => {
    const task = this.scheduler.dequeue(resource.alias);
    if (task) await this.processTaskOnResource(task, resource);
  });
  await Promise.allSettled(taskPromises);
  
  // If any backlogs are below watermark, trigger queue fill
  if (this.scheduler.needsMoreWork()) {
    await this.fillQueue();
  }
}
```

**Back-pressure rules:**
- Each resource has a backlog cap (default 3 tasks)
- Queue fill triggers when total pending across all backlogs drops below `resourceCount * 2`
- Orchestrator's own resource is reserved for review/verification tasks — it processes from its own backlog only after distributing work to others first
- Failed tasks return to the unassigned pool for rerouting

## 15. Phase 11 — Polling Optimization

*Eliminate excessive Ollama API polling.*

### Current Problem

Agent monitors poll `/api/version` and `/api/tags` every ~30 seconds on every device. This is visible in all Ollama serve terminals as constant request noise.

### Solution: Event-Driven Discovery with Cache Headers

**Implementation in `src/resource-discovery.ts`:**

1. **Cache probe results** with TTL:
   ```typescript
   const probeCache: Map<string, { result: DiscoveredResourceModels; cachedAt: number }> = new Map();
   const PROBE_CACHE_TTL_MS = 300_000; // 5 minutes
   
   export async function probeResourceModelsCached(
     baseUrl: string,
     apiStyle: EndpointApiStyle,
     fetchFn?: FetchFn,
     apiKeyEnv?: string
   ): Promise<DiscoveredResourceModels> {
     const cacheKey = `${baseUrl}|${apiStyle}`;
     const cached = probeCache.get(cacheKey);
     if (cached && Date.now() - cached.cachedAt < PROBE_CACHE_TTL_MS) {
       return cached.result;
     }
     const result = await probeResourceModels(baseUrl, apiStyle, fetchFn, apiKeyEnv);
     probeCache.set(cacheKey, { result, cachedAt: Date.now() });
     return result;
   }
   ```

2. **Replace monitor polling** with on-demand discovery:
   - Probe on first connection (setup/startup)
   - Probe on `/resource refresh {alias}` command
   - Probe when a task fails with model-not-found error
   - Probe after N tasks (configurable, default 100) as background refresh
   - Do NOT poll on a timer

3. **Use response headers for version info:**
   - Ollama includes version info in response headers during normal chat requests
   - Extract and cache during `callModel()` — no separate version poll needed

**Files:** `src/resource-discovery.ts`, `src/app.ts`, `test/core.test.ts`

### Estimated Impact
- Current: ~120 polls/hour across 4 devices (2/min × 4)
- After: ~4 polls/hour (on-demand only)
- 97% reduction in polling overhead

```bash
echo "block in on en0 proto tcp from any to any port { $OLLAMA_PORT, $LOCALCREW_API_PORT }" >> /tmp/localcrew-pf-rules

if [ "$CONFIRM" = "y" ] || [ "$CONFIRM" = "Y" ]; then

  echo "Skipped. Rules saved to /tmp/localcrew-pf-rules"
```

### 13D: Daily Session Lifecycle

**Problem:** The marathon demonstrated that unbounded `/auto` runs produce diminishing returns — tasks become speculative, quality degrades, and the orchestrator loses coherence after extended operation without a structured session boundary.

**Requirement from directives:**
> *"When a daily work session is active, treat it as a bounded commitment: complete the queued tasks, then signal `DAILY_COMPLETE` when the work is done. The daily digest is a deliverable."*

**Implementation:**

#### Session Bounding

Add a `DailySession` type to `types.ts`:

```typescript
interface DailySession {
  sessionId: string;            // ISO date: "2026-03-15"
  startedAt: string;            // ISO timestamp
  tasksBound: number;           // tasks queued at session start
  tasksCompleted: number;       // tasks finished this session
  tasksFailed: number;          // tasks that failed this session
  status: "active" | "complete" | "aborted";
  completedAt?: string;         // when DAILY_COMPLETE was signaled
}
```

Store in `.localcrew/system/state.json` alongside the existing auto queue state.

#### `DAILY_COMPLETE` Signal

When the orchestrator empties its bounded task queue (all `tasksBound` tasks processed), it:
1. Sets `session.status = "complete"` and records `completedAt`
2. Generates a daily digest (see below)
3. Emits an SSE event: `{ type: "daily-complete", sessionId, summary }`
4. Stops autonomous queue-fill — does NOT start speculative new work
5. Logs an audit event with `scope: "daily-session"` and `action: "complete"`

If the user explicitly runs `/auto stop` before all tasks complete, set `status = "aborted"` and still generate the digest.

#### Daily Digest Generation

After `DAILY_COMPLETE`, generate a structured markdown digest:

```markdown
# Daily Digest — {sessionId}

## Summary
- Tasks completed: {n}/{total}
- Tasks failed: {m}
- Session duration: {duration}
- Resources used: {list}

## Completed Work
{task-by-task summary with quality verification status from Phase 1A's TaskVerificationResult}

## Failed Tasks
{task, error, diagnosis}

## Next Priorities
{inferred from remaining queue, focus-todo, and roadmap}
```

Store at `.localcrew/system/daily-digests/{sessionId}.md`. Respect the `dailyDigestDirective` user preference from `user-profile.md` if set — this controls the reporting tone and detail level.

#### Failure Quarantine & Recovery

When a task fails during a daily session:
1. Increment `tasksFailed` on the session
2. Log the failure with full context to the audit log
3. If the same resource fails 2+ tasks consecutively, quarantine it (set `quarantinedUntil` timestamp on the resource, skip it in routing for 10 minutes)
4. Apply the directive: *"Unexpected failures should trigger diagnosis, quarantine, and recovery, not repeated blind retries"*
5. After quarantine expires, route ONE lightweight probe task to the resource before resuming full assignment

#### Integration with Auto Mode

Modify `processAutoQueue()` in `app.ts`:

```typescript
// At session start (when /auto begins and no active session):
if (!state.dailySession || state.dailySession.status !== "active") {
  state.dailySession = {
    sessionId: new Date().toISOString().slice(0, 10),
    startedAt: new Date().toISOString(),
    tasksBound: state.pendingTasks.length,
    tasksCompleted: 0,
    tasksFailed: 0,
    status: "active",
  };
}

// After each task completes:
state.dailySession.tasksCompleted++;
if (state.dailySession.tasksCompleted + state.dailySession.tasksFailed 
    >= state.dailySession.tasksBound) {
  await signalDailyComplete(state);
}
```

### Before Extended Autonomous Run

1. `npm run validate` — clean
2. Start with `/auto` — observe first queue fill cycle
3. Verify per-resource distribution shows multiple resources active
4. Verify display gauges update from SSE
5. Verify no polling noise on agent Ollama terminals
6. Verify agent identity creation/reuse works
7. Verify post-task quality verification runs on each completed task
8. Verify CLI `/status` refreshes automatically without stale data
9. Verify model profile mode is respected (if set)
10. Run for 30 minutes supervised before leaving unattended
11. Check outbox for duplicate ticket generation (should be suppressed)
12. Verify daily session counter increments and `DAILY_COMPLETE` fires when queue empties

### Sub-Orchestrator Promotion Testing

Before trusting hierarchical delegation in production:
1. Promote Zora to sub-orchestrator via `/topology assign zora orchestrator`
2. Delegate a 3-task pipeline: `/topology delegate zora "research → summarize → verify"`
3. Verify Zora's subordinate agents receive routed subtasks
4. Verify results flow back to primary orchestrator audit log
5. Disconnect primary orchestrator — verify Zora continues operating independently
6. Reconnect — verify state reconciliation

### Rollback Safety

Each phase is independently deployable. If a phase breaks, revert just that module's changes. The phases are ordered so that:
- Safety fixes (P0) never depend on feature work
- Feature phases build on each other but can be skipped
- Display and CLI changes are cosmetic and independently revertable
