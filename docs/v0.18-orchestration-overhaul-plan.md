## 1. Executive Summary

The marathon test proved the core orchestration loop is functional: 44+ tasks processed across 4 devices, queue fill/review/finalize pipeline works, agent identity and dropbox workflows operate end-to-end. However, the run exposed systemic issues that must be resolved before the next extended autonomous session:

**Critical findings:**
- **130+ near-identical speculative feature request tickets** flooded the outbox — the redundancy/novelty gate problem
- **Model drift** — gpt-oss and qwen3-coder used where llama-first was expected
- **Rogue filesystem writes** outside sandbox boundaries
- **Completion claims without artifact verification**
- **Excessive polling** (twice/minute per device for version/tags)
- **Agent identities conflated with device resources** — no separation of identity from hardware
- **No per-resource task backlog** — resources sit idle while orchestrator processes serially
- **Context management** is broad-and-shallow instead of hot-swapped and targeted

**This plan replaces and supersedes the prior ticket pack (TKT-01 through TKT-13) with a cohesive phased architecture that addresses the consultant's recommendations while respecting the zero-dependency TypeScript codebase.**

## 2. Marathon Evidence Review

### Quantitative Snapshot

| Metric | Value |
|---|---|
| Tasks completed | 44 |
| Tasks pending | 1 |
| Auto-fill generated tasks | 38 |
| Feature request tickets generated | ~130 |
| Near-duplicate tickets | ~120 (estimated) |
| Missing claimed artifacts | 2 (web_search_demo_report.md, web_search_demo_steps.md) |
| Rogue root paths created | 1 (`# Updated Spec\n\nNew content.`) |
| Model distribution | llama3.1:latest(13), gpt-oss:20b(10), llama3.2:1b(13), qwen3-coder:latest(7), llama3.1:8b(1) |
| Empty/insufficient results | 3 |

### Key Observations

1. **Outbox ticket flood:** The queue fill loop generated speculative external-change tasks that got properly redirected to outbox feature request tickets — but the same speculative pattern repeated across dozens of queue-fill cycles, producing ~130 near-identical tickets about telemetry endpoints, metrics scripts, HUD widgets, and cleanup scripts.

2. **Model selection chaos:** `gpt-oss:20b` was used for 10 tasks and `qwen3-coder:latest` for 7 — these are high-VRAM models that cause swap pressure on constrained devices. The system lacks model swap penalty awareness.

3. **Serial processing:** Tasks executed one-at-a-time through the orchestrator, leaving 3 of 4 devices idle most of the time. No per-resource work queues exist.

4. **Identity confusion:** Resource aliases like `@desktop-m01slkb` appear in output where participant nicknames should. Agent identities and devices are loosely coupled.

5. **Context reset loops:** Self-improvement tasks restart from scratch each cycle instead of iterating on prior artifacts with explicit deltas.

6. **Polling overhead:** Agent monitors hit Ollama `/api/version` and `/api/tags` every 30 seconds — unnecessary load on inference endpoints.

## 3. Architecture Realignment

### Current Model (v0.17)

```
CrustyApp (monolith) → chooseResourceForTask (regex heuristic) → callModel → single serial loop
```

### Target Model (v0.18)

```
Orchestrator Identity (memory/directives/index)
  ├── Context Bundle Manager (hot-swap memory segments by task purpose)
  ├── Task Scheduler (per-resource backlogs with back-pressure)
  │     ├── Resource A backlog → inference calls
  │     ├── Resource B backlog → inference calls
  │     └── Resource C backlog → inference calls
  ├── Agent Identity Factory (markdown-based, dynamically created)
  │     ├── Agent "data-analyst" → bound to Resource B
  │     ├── Agent "reviewer" → bound to Resource A
  │     └── Agent "utility-worker" → rotates across low-tier resources
  ├── Capability Scorer (hardware-aware, load-aware, context-aware)
  ├── Model Selector (task-purpose-aware, swap-penalty-aware)
  └── Telemetry (fuzzy T/s estimation, light-touch, event headers)
```

### Core Principles (from consultant + codebase reality)

1. **Devices are resources; agents are identities.** Device names are local, untracked, dynamically created at install. Agent identities are portable markdown bundles.
2. **Increase context before increasing model size.** Never auto-upgrade models.
3. **Prefer horizontal scaling** (more resources working in parallel) over vertical (bigger models on one device).
4. **Measure before routing.** Use capability scores, not just regex keyword matching.
5. **Hot-swap context, don't dump everything.** Load only the memory bundles needed for the current task purpose.
6. **Maintain back-pressure.** Keep every resource's backlog populated so nothing idles.
7. **Favor stability over theoretical max.** Conservative context caps. Never exceed tier limits.

## 4. Phase 0 — Critical Fixes

*These must land before any feature work. They fix safety and correctness bugs.*

### P0-A: Filesystem Sandbox Hardening

**Problem:** Autonomous writes created `# Updated Spec\n\nNew content.` at repo root.

**Implementation in `src/app.ts`:**
- Add `ALLOWED_WRITE_ROOTS` constant mapping stages to allowed paths:
  ```
  internal → .crusty/system/**
  active → external-memory/active/**
  outbox → external-memory/outbox/**
  ```
- In `ensureSafeGeneratedRelativePath()`, add canonical path normalization rejecting:
  - Paths containing newline/control characters
  - Paths resolving outside their stage root after `path.resolve()`
  - Hidden dot-prefixed segments (except `.crusty` itself)
- Emit structured audit event on every denied write with attempted path and rejection reason.

**Files:** `src/app.ts`, `src/dropbox.ts`, `src/telemetry.ts`, `test/security.test.ts`

### P0-B: Artifact Verification Gate

**Problem:** Tasks claimed `WRITE[outbox][web_search_demo_report.md]` but files don't exist.

**Implementation in `src/app.ts`:**
- After processing WRITE blocks and before marking task completed, verify:
  - Each claimed file exists at the expected path
  - Each file is non-empty (>0 bytes)
- On verification failure:
  - Mark task status as `"failed"` (new status value) instead of `"completed"`
  - Record `errorMessage` with specific missing artifact details
  - Do NOT auto-queue remediation — just fail clearly

**Files:** `src/app.ts`, `src/orchestrator-store.ts`, `src/types.ts` (add `"failed"` to task status union), `test/app.test.ts`

### P0-C: Novelty Gate and Duplicate Suppression

**Problem:** ~130 near-identical feature request tickets; repeated self-improvement loops.

**Implementation:**

1. **Task fingerprinting** — new function in `src/utils.ts`:
   ```typescript
   export function computeTaskFingerprint(content: string): string
   ```
   - Normalize: lowercase, strip punctuation, collapse whitespace
   - Extract top 8 content words (skip stop words)
   - Sort and join → deterministic fingerprint string

2. **Queue dedupe** — in `src/app.ts` `addPendingTask()`:
   - Before adding, check fingerprint against:
     - All pending tasks
     - Last N (configurable, default 50) completed tasks
   - If fingerprint match found within TTL window (default 2 hours), suppress with log

3. **Outbox dedupe** — in WRITE[outbox] handler:
   - Before writing feature request, check fingerprint against existing outbox files
   - If near-duplicate exists, append to existing file or suppress entirely

4. **Self-improvement iteration contract** — in `buildAutoTaskMessages()`:
   - Add system instruction: "If this task relates to prior work, you MUST reference the prior artifact path and state what specific delta you are making. Do not restart analysis from scratch."

**Files:** `src/utils.ts`, `src/app.ts`, `src/messages.ts`, `test/app.test.ts`

### P0-D: Queue Compose Safety

**Problem:** REPL input races with auto-pulse output, causing duplicate submissions.

**Implementation in `src/index.ts`:**
- Add 60-second TTL dedupe cache for user-submitted queue messages (normalized content → timestamp)
- When duplicate detected, print "Duplicate suppressed" instead of queueing
- Add `CRUSTY_AUTO_COMPOSE_PAUSE_MS` env var (default 0): when set, auto-pulse pauses for N ms after user submits input

**Files:** `src/index.ts`, `src/app.ts`

*Core architectural change: agents are markdown-stored identity bundles, separate from devices.*

### 1C: Resource Delegation to Agent Identities

When the orchestrator enters `/auto`, the initialization phase should:

1. Load orchestrator memory index and focus-todo
2. Review available resources and their current state
3. Create or reuse agent identities appropriate for the work:

4. Populate per-resource task backlogs from the queue

**Scoring weights (adapted from consultant, tuned for our setup):**

```typescript
const SCORE_WEIGHTS = {
  availability: 0.4,    // 1.0 - (queueDepth / MAX_QUEUE_DEPTH)
  memoryHeadroom: 0.3,  // 1.0 - ramUsagePct
```

**Capability match scoring:**

```typescript
function capabilityMatchScore(resource: ResourceProfile, task: TaskMetadata): number {
  if (task.reasoningDepth === "high") {
    return resource.tier === "top" ? 1.0 : 0.4;
  }
  if (task.tokenEstimate > 8000) {
    return resource.tier === "top" ? 1.0 : 0.2;
  }
  if (task.taskType === "extraction" || task.taskType === "classification") {
    return resource.tier === "low" ? 0.9 : 0.7;
  }
  return 0.8;
}
```

## 7. Phase 3 — Context Safety Controller

*Enforce context caps by tier. Never exceed safe limits.*

### Context Caps (from consultant, adjusted for our models)

| Tier | Safe Cap | Notes |
|---|---|---|
| O (top/orchestrator) | 32768 | Mac M4 32GB can handle this |
| S (sub-orchestrator) | 16384 | Win 24-core 15.7GB (Zora) |
| A (agent) | 4096 | Mac 8GB (Min), Win 15.9GB (Pav) |

### Implementation

**New function in `src/resources.ts`:**

```typescript
export function getContextCap(resource: ResourceProfile): number {
  if (resource.maxContextTokens && resource.maxContextTokens > 0) {
    return resource.maxContextTokens;
  }
  // Tier-based defaults
  switch (resource.tier) {
    case "top": return 32768;
    case "mid": return 16384;
    case "low": return 4096;
  }
}

export function computeSafeContextAllocation(
  resource: ResourceProfile,
  telemetry: ResourceTelemetry,
  task: TaskMetadata
): number {
  const desired = task.tokenEstimate * 2; // Room for response
  const cap = getContextCap(resource);
  let ctx = Math.min(desired, cap);
  
  if (telemetry.ramUsagePct > 85) ctx = Math.floor(ctx * 0.5);
  
  return Math.max(ctx, 2048);
}
```

**Integration with `buildAutoTaskMessages()`:**
The existing `maxContextTokens` parameter and `budgetContextBlocks()` already handle prompt assembly. We enhance by:
1. Always passing `maxContextTokens` from `getContextCap()` 
2. Adding the context allocation to the Ollama request body via `num_ctx` parameter

**New in `src/ollama.ts`:**
- When API style is `"ollama"`, include `num_ctx` in the request options based on `computeSafeContextAllocation()`
- This tells Ollama exactly how much context to allocate, preventing OOM

**Files:** `src/resources.ts`, `src/ollama.ts`, `src/messages.ts`, `test/core.test.ts`

## 8. Phase 4 — Dynamic Model Selection

*Task-and-resource-aware model selection with swap penalty awareness.*

### Current State

`selectModel()` in `src/resources.ts` checks purpose-specific slots (codingModel, reasoningModel, toolsModel) and falls back to defaultModel. `detectTaskPurpose()` uses regex to classify. This is functional but naive.

### Enhancement: Model Priority Map with Swap Penalty

**New in `src/resources.ts`:**

```typescript
interface ModelSwapState {
  currentLoadedModel: string | null;
  lastSwapAt: number;              // timestamp ms
}

// Track per-resource what model is currently loaded
// (inferred from last successful callModel response)
const modelSwapState: Map<string, ModelSwapState> = new Map();

export function selectModelForTask(
  resource: ResourceProfile,
  task: TaskMetadata,
  currentlyLoaded: string | null
): { model: string; swapRequired: boolean; swapPenaltyMs: number } {
  const optimalModel = selectModel(resource, task.taskType === "reasoning" ? "reasoning" 
    : task.taskType === "classification" || task.taskType === "extraction" ? "tools"
    : "default");
  
  const swapRequired = currentlyLoaded !== null && currentlyLoaded !== optimalModel;
  
  // Estimate swap penalty: ~2-8s for small models, 10-30s for large
  const swapPenaltyMs = swapRequired ? estimateSwapPenalty(optimalModel) : 0;
  
  // If swap penalty is high and current model can handle the task adequately,
  // prefer keeping the current model loaded
  if (swapRequired && swapPenaltyMs > 5000 && canModelHandleTask(currentlyLoaded!, task)) {
    return { model: currentlyLoaded!, swapRequired: false, swapPenaltyMs: 0 };
  }
  
  return { model: optimalModel, swapRequired, swapPenaltyMs };
}
```

## 10. Phase 6 — Per-Resource Task Backlog & Back-Pressure

*Keep every resource busy. No device should idle while work is available.*

### Current State

`CrustyApp` has a single `systemState.auto.pending` queue processed serially. One task at a time. Resources idle.

### Target: Multi-Queue Scheduler

**New file: `src/scheduler.ts`**

```typescript
export interface ResourceBacklog {
  resourceAlias: string;
  tasks: AutoQueueTask[];
  maxDepth: number;          // Back-pressure cap (default: 3)
  isProcessing: boolean;
  currentTaskId: number | null;
}

export class TaskScheduler {
  private backlogs: Map<string, ResourceBacklog> = new Map();
  
  // Distribute pending tasks across resource backlogs
  distribute(
    pending: AutoQueueTask[],
    resources: ResourceProfile[],
    telemetry: Map<string, ResourceTelemetry>,
    scorer: (resource: ResourceProfile, task: TaskMetadata) => number
  ): void;
  
  // Get next task for a specific resource
  dequeue(resourceAlias: string): AutoQueueTask | null;
  
  // Check if any resource has capacity
  hasCapacity(): boolean;
  
  // Get back-pressure status
  getBackPressure(): Map<string, { depth: number; maxDepth: number }>;
  
  // Rebalance when resource comes online/offline
  rebalance(): void;
}
```

**Integration with auto-pulse:**

```typescript
// BEFORE: single serial task processing
async pulse(): Promise<void> {
  const nextTask = this.getNextPendingTask();
  if (nextTask) await this.processTask(nextTask);
}

// AFTER: parallel resource processing
async pulse(): Promise<void> {
  const idleResources = this.scheduler.getIdleResources();
  const taskPromises = idleResources.map(async (resource) => {
    const task = this.scheduler.dequeue(resource.alias);
    if (task) await this.processTaskOnResource(task, resource);
  });
  await Promise.allSettled(taskPromises);
  
  // If any backlogs are below watermark, trigger queue fill
  if (this.scheduler.needsMoreWork()) {
    await this.fillQueue();
  }
}
```

**Back-pressure rules:**
- Each resource has a backlog cap (default 3 tasks)
- Queue fill triggers when total pending across all backlogs drops below `resourceCount * 2`
- Orchestrator's own resource is reserved for review/verification tasks — it processes from its own backlog only after distributing work to others first
- Failed tasks return to the unassigned pool for rerouting

## 13. Phase 9 — Polling Optimization

*Eliminate excessive Ollama API polling.*

### Current Problem

Agent monitors poll `/api/version` and `/api/tags` every ~30 seconds on every device. This is visible in all Ollama serve terminals as constant request noise.

### Solution: Event-Driven Discovery with Cache Headers

**Implementation in `src/resource-discovery.ts`:**

1. **Cache probe results** with TTL:
   ```typescript
   const probeCache: Map<string, { result: DiscoveredResourceModels; cachedAt: number }> = new Map();
   const PROBE_CACHE_TTL_MS = 300_000; // 5 minutes
   
   export async function probeResourceModelsCached(
     baseUrl: string,
     apiStyle: EndpointApiStyle,
     fetchFn?: FetchFn,
     apiKeyEnv?: string
   ): Promise<DiscoveredResourceModels> {
     const cacheKey = `${baseUrl}|${apiStyle}`;
     const cached = probeCache.get(cacheKey);
     if (cached && Date.now() - cached.cachedAt < PROBE_CACHE_TTL_MS) {
       return cached.result;
     }
     const result = await probeResourceModels(baseUrl, apiStyle, fetchFn, apiKeyEnv);
     probeCache.set(cacheKey, { result, cachedAt: Date.now() });
     return result;
   }
   ```

2. **Replace monitor polling** with on-demand discovery:
   - Probe on first connection (setup/startup)
   - Probe on `/resource refresh {alias}` command
   - Probe when a task fails with model-not-found error
   - Probe after N tasks (configurable, default 100) as background refresh
   - Do NOT poll on a timer

3. **Use response headers for version info:**
   - Ollama includes version info in response headers during normal chat requests
   - Extract and cache during `callModel()` — no separate version poll needed

**Files:** `src/resource-discovery.ts`, `src/app.ts`, `test/core.test.ts`

### Estimated Impact
- Current: ~120 polls/hour across 4 devices (2/min × 4)
- After: ~4 polls/hour (on-demand only)
- 97% reduction in polling overhead

## 14. Phase 10 — Network Firewall Automation

*Setup scripts that configure inter-device firewall access.*

### macOS Script: `scripts/setup-firewall-macos.sh`

```bash
#!/bin/bash
# Configure macOS firewall to allow Ollama access from trusted devices
# Run during agent setup after config is populated

set -euo pipefail

OLLAMA_PORT="${OLLAMA_PORT:-11434}"
CRUSTY_API_PORT="${CRUSTY_API_PORT:-4310}"

echo "=== Crusty Network Access Setup (macOS) ==="

# Read trusted IPs from config
if [ ! -f ".crusty/resources.json" ]; then
  echo "Error: .crusty/resources.json not found. Run setup first."
  exit 1
fi

# Extract IPs from resource base URLs
TRUSTED_IPS=$(node -e "
  const r = require('./.crusty/resources.json');
  const urls = Object.values(r.resources).map(x => new URL(x.baseUrl).hostname);
  console.log([...new Set(urls)].filter(ip => ip !== '127.0.0.1').join('\n'));
")

echo "Trusted device IPs:"
echo "$TRUSTED_IPS"
echo ""

# macOS uses pf (packet filter)
# Generate pf rules
PF_ANCHOR_FILE="/etc/pf.anchors/crusty"

echo "# Crusty inter-device access rules" > /tmp/crusty-pf-rules
for IP in $TRUSTED_IPS; do
  echo "pass in quick on en0 proto tcp from $IP to any port { $OLLAMA_PORT, $CRUSTY_API_PORT }" >> /tmp/crusty-pf-rules
done
# Block all other access to these ports
echo "block in on en0 proto tcp from any to any port { $OLLAMA_PORT, $CRUSTY_API_PORT }" >> /tmp/crusty-pf-rules

echo "Generated firewall rules:"
cat /tmp/crusty-pf-rules
echo ""
read -p "Apply these rules? (y/N): " CONFIRM
if [ "$CONFIRM" = "y" ] || [ "$CONFIRM" = "Y" ]; then
  sudo cp /tmp/crusty-pf-rules "$PF_ANCHOR_FILE"
  sudo pfctl -f /etc/pf.conf
  echo "✓ Firewall rules applied."
else
  echo "Skipped. Rules saved to /tmp/crusty-pf-rules"
fi
```

### Windows Script: `scripts/setup-firewall-windows.ps1`

```powershell
# Configure Windows Firewall for Crusty inter-device access
# Run as Administrator during agent setup

$OllamaPort = if ($env:OLLAMA_PORT) { $env:OLLAMA_PORT } else { 11434 }
$CrustyApiPort = if ($env:CRUSTY_API_PORT) { $env:CRUSTY_API_PORT } else { 4310 }

Write-Host "=== Crusty Network Access Setup (Windows) ===" -ForegroundColor Cyan

# Read trusted IPs from config
$configPath = ".crusty/resources.json"
if (-not (Test-Path $configPath)) {
    Write-Host "Error: $configPath not found. Run setup first." -ForegroundColor Red
    exit 1
}

$resources = Get-Content $configPath | ConvertFrom-Json
$trustedIps = $resources.resources.PSObject.Properties.Value | 
    ForEach-Object { ([Uri]$_.baseUrl).Host } |
    Where-Object { $_ -ne "127.0.0.1" } |
    Select-Object -Unique

Write-Host "Trusted device IPs: $($trustedIps -join ', ')"
Write-Host ""

$confirm = Read-Host "Create firewall rules for these IPs? (y/N)"
if ($confirm -eq 'y' -or $confirm -eq 'Y') {
    # Remove existing Crusty rules
    Get-NetFirewallRule -DisplayName "Crusty*" -ErrorAction SilentlyContinue | Remove-NetFirewallRule

    foreach ($ip in $trustedIps) {
        # Allow Ollama access from trusted IP
        New-NetFirewallRule -DisplayName "Crusty Ollama from $ip" `
          -Direction Inbound -Protocol TCP -LocalPort $OllamaPort `
          -RemoteAddress $ip -Action Allow | Out-Null
        
        # Allow Crusty API access from trusted IP  
        New-NetFirewallRule -DisplayName "Crusty API from $ip" `
          -Direction Inbound -Protocol TCP -LocalPort $CrustyApiPort `
          -RemoteAddress $ip -Action Allow | Out-Null
    }
    
    Write-Host "✓ Firewall rules created." -ForegroundColor Green
} else {
    Write-Host "Skipped."
}
```

### Integration with Setup Flow

In `scripts/setup-agent.js`, after resource configuration is saved:
1. Detect platform (`process.platform`)  
2. Prompt: "Configure firewall for inter-device access? (y/N)"
3. If yes, spawn the appropriate script with the config data
4. Report success/failure

**Files:** `scripts/setup-firewall-macos.sh` (new), `scripts/setup-firewall-windows.ps1` (new), `scripts/setup-agent.js` (integration), `docs/setup.md` (documentation)
